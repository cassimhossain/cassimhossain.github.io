Building an ESP32 4WD Robot

A complete guide to building a responsive, wireless-controlled 4-wheel drive platform with real-time motor control and obstacle sensing — from chassis assembly through firmware deployment.

Qasim Mushtaq  ·  January 15, 2026  ·  ~10 min read

The problem

Most beginner robotics platforms use servo-driven wheels or single-motor designs, which limits torque and agility. Building a true 4WD platform that responds instantly to commands over WiFi requires careful motor synchronization, proper power distribution, and firmware that can handle concurrent PWM signals to four independent motors.

This project emerged from classroom constraints: we needed a platform that could work reliably in a STEM environment, be repaired quickly with off-the-shelf parts, cost under $60 per unit, and teach students real motor control—not just toy servos. The 4WD design also enabled obstacle detection and dynamic course navigation without custom sensors.

Hardware

The build centers on an ESP32 microcontroller paired with a dual-channel motor driver and four 3-12V geared DC motors. Here's what makes this design practical:

  • Microcontroller: ESP32 DevKit (dual-core, WiFi, 2x PWM-capable pins per motor)
  • Motor Driver: L298N or DRV8833 dual-channel controller (handles 4 motors via two drivers)
  • Motors: 3-6V geared DC motors (85-200 RPM, 1kg-cm torque) from robotics suppliers
  • Chassis: 4WD robot car chassis kit (~$15, pre-drilled for motor mounts)
  • Power: 2× 18650 Li-Ion batteries in parallel (7.4V nominal, 2600mAh)
  • Sensors: HC-SR04 ultrasonic module (front-facing for obstacle detection)
  • Communication: WiFi via ESP32 (no separate RF module needed)

Wiring schematic

Connect motors to the driver as follows. I use GPIO pins for PWM to allow independent speed control on each wheel:

  • ESP32 GPIO 12 → L298N IN1 (Motor A forward)
  • ESP32 GPIO 13 → L298N IN2 (Motor A reverse)
  • ESP32 GPIO 14 → L298N IN3 (Motor B forward)
  • ESP32 GPIO 27 → L298N IN4 (Motor B reverse)
  • ESP32 GPIO 25 → L298N ENA (Motor A speed/PWM)
  • ESP32 GPIO 26 → L298N ENB (Motor B speed/PWM)
  • HC-SR04 TRIG → GPIO 5, ECHO → GPIO 18

Firmware architecture

The control loop runs at 100 Hz, reading sensor data and executing movement commands in parallel. I use FreeRTOS tasks to keep motor updates responsive even when WiFi traffic arrives. 

// Motor control structure
struct Motor {
  uint8_t pwm_pin;
  uint8_t fwd_pin, rev_pin;
  uint8_t speed; // 0-255
};

Motor motors[4] = {
  {25, 12, 13, 0}, // Front-left
  {25, 12, 13, 0}, // Front-right
  {26, 14, 27, 0}, // Back-left
  {26, 14, 27, 0}  // Back-right
};

void setMotorSpeed(Motor &m, int speed) {
  speed = constrain(speed, -255, 255);
  digitalWrite(speed > 0 ? m.fwd_pin : m.rev_pin, HIGH);
  digitalWrite(speed > 0 ? m.rev_pin : m.fwd_pin, LOW);
  analogWrite(m.pwm_pin, abs(speed));
}

void loop() {
  // Obstacle detection
  int distance = readUltrasonic();
  if (distance < 15) {
    stopAllMotors();
    return;
  }
  
  // Command from WiFi/BLE controller
  executeMovement(current_command);
}
What went wrong first: DC motor speed varies with battery voltage. Early tests showed erratic behavior when the battery dropped below 7V. Solution: implement a voltage-adaptive PWM table so the robot maintains consistent speed regardless of charge state. Also, ESPs default PWM frequency is 5kHz, which creates an audible whine; I switched to 20kHz.

Motor synchronization

Four independent motors don't turn at exactly the same speed. This causes the robot to drift during straight-line movement. The fix: measure motor speed via interrupts on the encoder inputs (if available) or use a simple closed-loop: if one side drifts, reduce its PWM slightly and increase the other. For quick prototyping, a lookup table of empirical offsets works well. 

// Empirical calibration: motors vary by ~5-10%
const uint8_t speed_table[4][256] = {
  // Front-left: measured to run ~8% faster
  { 0, 5, 10, 15, ... }, // Reduce PWM to sync
  // Front-right: reference
  { 0, 10, 20, 30, ... },
  // Back-left: measured to run ~12% slower
  { 0, 12, 24, 36, ... }, // Increase PWM to sync
  // Back-right: reference
  { 0, 10, 20, 30, ... }
};

void driveForward(uint8_t speed) {
  for(int i = 0; i < 4; i++) {
    setMotorSpeed(motors[i], speed_table[i][speed]);
  }
}

Results

The final robot achieves:

  • Acceleration: 0–30 cm/s in 400ms
  • Turning radius: ~8cm (full rotation in 2.5 seconds)
  • Range: ~15 meters WiFi control (line-of-sight)
  • Runtime: 45 minutes on 2× 18650 cells at 50% duty
  • Obstacle detection: 5–150cm, accurate within ±2cm

In classroom trials, students were able to debug motor synchronization issues independently and expand the platform with line-following sensors. The modular firmware structure made it easy to swap in new control algorithms (e.g., PID for line-following) without rewriting motor handling.

What I'd do differently

Use brushless outrunners. Brushed motors have inconsistent torque ripple; brushless DC motors deliver smoother acceleration and require less tuning. They cost 2–3× more but simplify the firmware dramatically.

Add wheel encoders from the start. A simple optical encoder (IR LED + photodiode) on each wheel would eliminate speed-matching tables and enable proper odometry for autonomous navigation.

Separate power rails. Running motors and logic from the same battery causes voltage sag that crashes the ESP32. A dedicated buck converter for the microcontroller ($3) prevents this headache entirely.
